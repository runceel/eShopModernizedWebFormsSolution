# 0007: 初期化の状態と失敗時の境界

- 状態: Accepted
- 記録日: 2026-11-13
- 関連: [OD-04](https://github.com/runceel/eShopModernizedWebFormsSolution/issues/5)、[OD-07](https://github.com/runceel/eShopModernizedWebFormsSolution/issues/8)、[OD-14](https://github.com/runceel/eShopModernizedWebFormsSolution/issues/15)
- 補足: [ADR 0003](0003-persistence-and-initialization.md) の初期化方針を具体化し、置き換えない。

## 背景

初期化サービスは PostgreSQL とファイル上の画像を準備し、API は成功前に通常操作を開始できない。商品をすべて削除した DB や初期化が中断された DB を新品と誤認すると、再投入や既存データの上書きにつながる。DB と画像には共通のトランザクションを前提にできない。

## 決定

カタログとともに初期化の開始・成功状態を永続化し、新規で空と確認できる管理領域だけを初回投入の対象とする。初回シードと成功記録は同じ DB トランザクションで確定し、画像の準備と採番の整合性も確認する。成功済み DB は再投入せず、状態不明・中断・不整合時は通常操作を止めて通知し、安全な復旧を要する。

AppHost は初期化サービスの成功後に API の通常操作を可能にし、別経路の起動でもこの境界を守る。現在の規則は[起動時の初期化](../target-spec/01-technical-spec.md#起動時の初期化)を参照する。

## 検討した選択肢

- 商品件数や Migrations 履歴で判断すると、意図的な全削除や途中失敗を正常な初回起動と区別できない。
- 記録なしの既存 DB を自動でシード・上書きする案は、所有者やデータの由来を確認できず採用しない。
- DB と画像を一括で原子的に更新する前提は置かず、完了を確認できない場合は停止する。

## 結果

- 空の商品一覧を維持でき、DB 内のシードと成功記録の部分確定を防げる。
- 既存データや画像、未完了状態を自動的に修復せず、操作者による確認・復旧が必要になる場合がある。
- 状態記録、画像の安全な配置、初期化の重複実行防止、Migrations と採番調整の失敗・中断時の具体的な実装と検証が必要になる。リセットの同期・復旧方式は別途扱う。
