# 0008: 商品の楽観的同時更新制御とドラフト保護

- 状態: Accepted
- 記録日: 2026-11-16
- 関連: [OD-13](https://github.com/runceel/eShopModernizedWebFormsSolution/issues/14)、[OD-17](https://github.com/runceel/eShopModernizedWebFormsSolution/issues/18)

## 背景

現行は商品を全項目更新し、同時更新を検知しないため、後から保存した古い内容が先行変更を失わせる。移行先は Web と API を分離し、PostgreSQL を唯一のカタログ永続化先とする。競合時の入力を失わない操作も必要である。

## 決定

商品単位の楽観的同時実行制御を第 1 ゴールから採用する。取得版を Web から API に渡し、API と DB が原子的な条件付き更新によって先行変更を保護する。Web は競合応答後のドラフトを所有し、利用者の明示的な破棄確認まで保持する。確認された最新データ読み込みの成功、または確認された編集離脱によってのみドラフトを破棄する。強制保存や自動マージは提供しない。現在の契約は[技術スペック](../target-spec/01-technical-spec.md#商品の同時更新制御od-13)と[機能仕様](../target-spec/02-functional-spec.md#同時更新)を参照する。

## 検討した選択肢

- 現行どおり後勝ち・競合後の強制保存は他者の変更を失わせるため採用しない。
- 悲観的ロックは人の入力時間にわたるロック所有・期限・解除を必要とし、保存時検知には不要なため採用しない。
- 自動再読込はドラフトを失わせ、自動マージは項目ごとの優先順位を要するため採用しない。
- 保存直前の読み取り比較だけでは、その後の競合を防げないため採用しない。

## 結果

- 先行変更と競合した利用者の入力を、DB と Web の異なる責務で保護できる。
- 利用者には最新データを基準に再編集する負担が残り、競合を成功扱いしない API とドラフトを失わない画面状態が必要になる。
- 物理トークン方式は EF Core / Npgsql の対応を確認して選び、特定の PostgreSQL 内部列を固定しない。
- API の同時送信と独立した二セッションでの画面操作を検証する。接続断やブラウザー終了を越えるドラフト保存、削除操作自体の競合契約は含めない。
